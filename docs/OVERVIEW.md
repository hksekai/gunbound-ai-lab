# GunBound AI Lab - Technical Overview

*Current prototype overview, September 16, 2026.*

**GunBound AI Lab is a local, private-server prototype that lets a human play classic GunBound against automated opponents.** It combines an existing compatible game/server bundle with custom Windows automation, native game-state inspection, and a tactical aiming controller.

The important distinction is that **each bot runs a real GunBound client**. These are not lightweight server-side players or headless protocol bots, and combat decisions are not generated by a large language model.

## 1. Where the project's files come from

The lab is a custom integration project, not a downloaded turnkey "GunBound AI server."

| Component | Origin and role |
|---|---|
| Game client and original assets | Supplied through the local **GunBound Retro Server Files** bundle. Its installer, `GunBoundWC_R_7.msi`, identifies itself as **GunBound WC Retro v7**, package version `1.0.7`. |
| Legacy server programs | The supplied bundle includes `Gunboundserv3.exe`, `GunBoundBroker3.exe`, optional buddy components, and a SQL dump containing 57 table definitions. |
| Custom lab code | The launchers, VM management, bot coordination, tactical logic, diagnostics and safeguards were developed locally in C# and PowerShell during this project. |
| Protocol references | [jglim's GunBound projects](https://github.com/jglim/gunbound-server), including their MIT-licensed protocol documentation and implementations. **We are not running jglim's Python emulator as our backend.** |
| Initial aiming references | Numerical trajectory work from [SanjoSolutions/gunbound-aimbot](https://github.com/SanjoSolutions/gunbound-aimbot), released under the Unlicense. Our current controller is a custom implementation, not that project running unchanged. |
| Compatibility/runtime components | The bundled DxWnd wrapper, Oracle VirtualBox, Windows Server Desktop Experience, and portable MariaDB. Each retains its own licensing requirements. |

The original upstream distribution and licensing chain of the supplied Retro bundle have **not** been independently established. The lab does not relicense the original client, artwork or server binaries.

Original supplied files are kept separate from the lab's working copies. Compatibility changes are narrowly scoped and fingerprint-checked; a different game executable is not assumed to be compatible.

## 2. Architecture

```text
Windows host PC
  Player's GunBound client
  Launcher and session supervisor
             |
       Host-only network
             |
One VirtualBox Windows guest
  Broker + world server
  Legacy SQL compatibility adapter
  MariaDB database

  BotOne   - real client + C# controller
  BotTwo   - real client + C# controller
  BotThree - real client + C# controller

  Shared interactive desktop and input arbiter
```

All three bots share **one VM**, currently configured with **6 GiB RAM and four virtual CPUs**. Six GiB is a working allocation, not a demonstrated minimum.

The guest uses Windows Server 2022 Desktop Experience. Its VirtualBox console can remain hidden, but Windows still maintains an interactive desktop and renders the game clients. **"Headless VM" does not mean "headless game clients."** The current Windows evaluation installation is not a substitute for obtaining appropriate licensing for ongoing use.

Player's window is displayed at **1600x1200**, scaling the original 800x600 image without changing its proportions. Bot windows remain **800x600**, matching the input and power-bar calibration.

### Server responsibilities

The broker supplies the server directory; the world server manages authentication, channels, rooms and match setup. Significant in-match behavior is handled by the native clients and their peer-to-peer communications.

That is why keeping the real clients is useful: **our controller chooses an action; the original client executes the game mechanics and exchanges the native gameplay messages.**

The backend uses MariaDB 11.4.13. A local compatibility adapter accommodates the old server's MySQL authentication expectations. SQL stays on guest loopback; game traffic uses the host-only network.

The active topology uses broker TCP port `8372`, world TCP/UDP port `8360`, and per-client UDP port `8363`. Each bot has its own private source address on the same guest adapter. These addresses are aliases, not additional VMs.

No public port forwarding or cloud hosting is configured. The optional buddy system and old web/account portal are not required for the active local gameplay path.

## 3. How sessions and bots start

The normal flow is:

1. The launcher starts the VM and waits for the backend to become healthy.
2. Player opens on the host PC.
3. The human joins Local Practice and creates a Solo room.
4. The supervisor reads the room's actual native capacity.
5. The guest launches the required bot clients, joins them, arranges teams and readies them.
6. The human clicks Start.

| Room size | Bot population |
|---|---|
| 2 players | Player versus BotOne |
| 4 players | Player + BotTwo versus BotOne + BotThree during automatic setup |
| 6 or 8 players | Explicitly unsupported |

Once a battle starts, the controller respects the **actual balanced native teams**, rather than freezing because the human started with a different teammate.

Each bot has a separate application root, account configuration, logs and process ownership records. The guest application is organized under `C:\GunBoundAI`; the protected backend and authoritative database are under `C:\GunBoundServer`.

Normal launching does not operate Player's mouse or keyboard. Temporary Player automation has been used only for specifically authorized testing.

### Why joining is still slow

**Preloading and warm standby are not implemented.** Bot clients currently start only after a supported room exists.

The coordinator also performs the full startup/join sequence serially. This initially simplified input safety, but holds the shared input lock longer than necessary. Room detection is tied to a roughly ten-second update cycle.

The planned optimization is to preload clients, overlap loading/network waits, and serialize only the short foreground input transactions - not blindly run three mouse/keyboard workers simultaneously.

## 4. How a bot understands the match

The controller combines two observation methods:

- **Read-only native memory inspection** for roster, teams, health, positions, wind, terrain, aiming limits, movement energy and turn identity.
- **Rendered-screen sampling** for the power bar.

These observations are tied to the **exact supplied client build**. Fingerprint checks reject unsupported binaries; the memory layout is not assumed to work with another GunBound version.

The bot follows the native turn sequence rather than assuming Player and BotOne alternate. This supports consecutive turns by the same actor and prevents repeated observations from causing duplicate shots.

This is also **not human-like visual perception**: the bot has access to precise game-state data. Difficulty changes proposed actions and search precision, not the truth of ownership, health or movement-safety observations.

## 5. Aiming, movement and terrain clearing

### Aiming

`aim.cs` implements a numerical Armor Shot 1 model. It evaluates trajectories using launch angle, power, wind, gravity and the current collision mask.

The planner uses native turret limits and accounts for facing and ground slope. True-angle bonus bands are preferences, not substitutes for the physical aiming limits.

Collision checks include terrain and living bodies. An intervening enemy must count as the first impact - even when the intended target is farther away - because that earlier explosion could endanger a teammate or the shooter.

The model remains an approximation. It does not reproduce every weapon, weather effect or damage rule.

### Power control

The controller does not simply hold Space for a fixed duration and assume the correct power.

It watches a **401-pixel strip of the native power bar**, releases at the requested point, and records observed power. This is why changing bot window size requires recalibration.

### Tactical positioning

`bot.cs` now compares living enemies and supported firing positions rather than committing exclusively to the nearest enemy.

It can choose to:

- Fire from the current position.
- Move to improve the shot, then fire.
- Spend a turn moving toward a better firing position.
- Clear useful blocking terrain.
- Pass when no safe, productive action remains.

Movement remains bounded. Current per-turn planning caps are **12 pixels for easy, 24 for medium and 48 for hard**. Short two-hop goals look ahead at most **96 pixels**; this is not map-wide pathfinding.

The bot re-observes its actual position after movement. Native movement-energy units are **not** assumed to equal pixels, and it will not deliberately walk over unsupported ground merely because a destination looks attractive.

### Digging

Terrain-clearing shots must predict a useful terrain impact and retain self-blast, teammate and supporting-ground protections. Off-map shots and trajectory timeouts do not qualify.

Observed terrain removal is tracked separately from predictions. Two unconfirmed or unproductive digging attempts stop that unchanged-target excavation loop.

## 6. Confidence, imperfection and working memory

The displayed percentage is **model robustness, not a calibrated hit probability**.

It measures how many of nine bounded angle/power perturbation probes reach the selected target without an earlier blocking collision. For example, six successful probes produce approximately 67% robustness - not proof of a 67% real-world hit rate.

Hard bots currently use acquisition variation of up to **+/-1 degree and +/-3 power units**, sampled once per native turn. This creates imperfect execution without corrupting authoritative telemetry or bypassing safety checks.

There is also a **four-entry, match-scoped shot memory**. Remembered angles and observed power are re-simulated against current conditions. A valid remembered shot reduces exploration variation to 20% before integer quantization.

**This memory feature still needs refinement:** the latest live run produced no eligible stored-shot reuse. Its current eligibility gate requires the target to remain alive at exactly the same coordinates, which can reject useful shots that displace a target or alter its supporting terrain.

A separate local Ollama/Qwen chat experiment exists, but **it is not in the combat decision loop**, and its in-game chat bridge is not established as a finished feature.

## 8. Small code excerpts for contributors

These excerpts come from the **custom lab source**, not from decompiled game/server code. Surrounding application-specific types, validation and control flow are omitted where noted. They illustrate the current approach; they are not standalone replacement scripts.

### Turn ownership: `bot.cs`

The controller checks native ownership, life and actor identity together:

```csharp
public bool MyTurn { get { return Mode == 11 && SelfAlive && Unit == Active && Turn && Slot == ActiveSlot; } }
```

Here `Mode == 11` identifies battle mode for the pinned client. This condition is used alongside native turn-sequence checks; seeing the same owned turn repeatedly does not authorize repeated firing.

### Comparing shot plans: `bot.cs`

`ChooseTactics` evaluates candidate targets and positions. This small helper gives clear shots priority and compares their scores:

```csharp
static bool BetterShot(ShotPlan candidate, ShotPlan best)
{
    return candidate != null && (best == null || (candidate.Shot.Clear && !best.Shot.Clear) ||
        (candidate.Shot.Clear == best.Shot.Clear && candidate.Score < best.Score -
        (!candidate.Shot.Clear && candidate.X != best.X ? 8 : 0)));
}
```

The surrounding planner also checks movement support, target identity, model robustness, timing budgets and actual geometry after movement. This helper is not permission to fire an otherwise unsafe shot.

### Respecting the first collision: `aim.cs`

This excerpt from `Trace` handles terrain and non-selected enemies before crediting a selected-target hit:

```csharp
int ix = (int)Math.Round(px), iy = (int)Math.Round(py);
if (terrain.Touches(ix, iy, radius))
    return new Shot(power, px, distance, py, seconds, false, friendlyImpact, true);
// ponytail: sample the first collision across all opposing bodies, not only the aim target.
// Non-selected bodies win sub-pixel ties conservatively; finer ordering needs swept native hitboxes.
if (otherEnemies != null)
    foreach (Body enemy in otherEnemies)
        if (enemy.Near(px, py, 0))
            return new Shot(power, px, distance, py, seconds, false, friendlyImpact,
                end: EndKind.OtherEnemy, hitSlot: enemy.NativeSlot);
```

The caller has already calculated the candidate point along the trajectory and checked friendly-path proximity. Subsequent logic checks the selected body. A high confidence score must not make an earlier interception or unsafe explosion disappear.

The integration itself uses wind-adjusted acceleration:

```csharp
double ax = Math.Truncate(Math.Cos(wind) * windPower) * windScale;
double ay = gravity - Math.Truncate(Math.Sin(wind) * windPower) * windScale;
if (ay <= 0) throw new ArgumentException("The supported model requires downward net gravity.");
double x = sourceX, y = sourceY, vx = speed * Math.Cos(angle), vy = -speed * Math.Sin(angle);
```

The bounded loop advances position and velocity in fixed steps, subdividing movement to avoid tunneling through thin terrain. The coefficients and geometry remain subject to native-client calibration.

### Reading the power bar: `lab-client.cs`

The power reader operates on a single captured row:

```csharp
static bool PowerRed(Color color)
{
    return color.R >= 90 && color.G < 65 && color.B < 85 && color.R > color.G * 2;
}

static int MeasurePower(Bitmap frame)
{
    Require(frame.Width == 401 && frame.Height == 1, "Unsupported power-bar sample geometry.");
    for (int point = 400; point >= 8; point -= 2)
        if (PowerRed(frame.GetPixel(point, 0))) return point;
    return 0;
}
```

The full charging routine separately verifies the 800x600 bot window, foreground ownership, turn continuity, legal power range and release of its own input. A pixel measurement is not a damage or hit confirmation.

### Capacity-driven population: `vm\shared-io.ps1`

Unsupported room sizes fail explicitly rather than silently launching fewer bots:

```powershell
function Get-RoomBotNames([int]$Capacity) {
    switch ($Capacity) {
        0 { return }
        2 { return 'BotOne' }
        4 { return @('BotOne','BotTwo','BotThree') }
        default { throw [ArgumentException]::new("Room capacity $Capacity is unsupported; choose a 2-player or 4-player room.") }
    }
}
```

The guest coordinator applies this only after validating the host-issued lease and native room target.

## 9. Safety and lifecycle design

Bots run as a non-administrator guest user. Server/database credentials and privileged control files are separated from bot application data.

Before acting, the system checks executable identity, process creation time, roster, team and turn ownership. A shared guest-input arbiter prevents one bot from stealing another's keyboard or mouse transaction.

Uncertain input ownership produces a persistent fault marker. It is not automatically erased to make the system appear healthy.

Player's supervisor renews a bounded **120-second lease**. Normal Player closure drains the bots and shuts down the backend/database before Windows. Persistent loss of authority also triggers cleanup. Brief file-publication races are retried without inventing a valid lease.

The private broker's server-list idle-expiry branch has been disabled for this lab. That does not disable real socket-error handling, the native room-master timeout, or Player-linked shutdown.

The database contains **MyISAM tables**, so forced VM shutdown is not equivalent to transactional rollback. Backups and post-crash checks matter. The active guest database is authoritative; the preserved host snapshot must not overwrite it after play.

## 10. Demonstrated behavior and current limitations

A recent live 1v1 observation on Miramo Town recorded:

- **10 BotOne Shot 1 charge/release events and no bot turn passes.**
- **Eight movement steps totaling 10 pixels.**
- **Five observed target-health decreases.**
- A maximum recorded planning time of **672 ms**.

Weather and falling complicate damage attribution, so those observations do not establish ten hits, five direct hits or a measured accuracy percentage.

The main remaining limitations are:

- **Shot 2 and SS are disabled.** Exact-client analysis identified different S2 muzzle fields and double-impact continuation. S2 needs build-specific runtime calibration before the proposed >=80% model-robustness direct-shot policy can be enabled.
- **Shot-memory reuse is not yet demonstrated live** and its eligibility rule appears too restrictive.
- **Room/battle transitions can still stop a worker.** One such error occurred before the later successful 1v1 observation.
- A **VM/kernel-level stall** occurred during earlier multi-client work. Restart recovered it, but its underlying cause remains unidentified.
- Latest smart-controller live evidence is primarily **1v1**. Earlier builds demonstrated three-bot 2v2 combat; the newest behavior still needs broader 2v2 regression runs.
- No warm standby, parallel startup pipeline, six/eight-player support, complete weather model, general pathfinder or advanced item/team strategy.
- Remote multiplayer and public hosting are not established.

Useful next contributions would be stronger transition handling, less restrictive but still safe shot-memory acquisition, reproducible tactical scenarios, measured startup/preloading improvements, and exact-client Shot 2 calibration.

## 11. Sharing and packaging

The useful shareable material is the **custom source, architecture, configuration templates and appropriately sanitized diagnostics**.

Do **not** distribute the `private` directories, VM disk, private deployment archives or database snapshots: they can contain credentials and account data. Native game binaries, artwork and compatibility libraries also require separate licensing/distribution consideration.

A distributable setup project should retain upstream license notices, generate fresh local credentials and installation identities, derive host paths from the chosen installation directory, and require users to supply legally obtained compatible game files. It should not ship a clone of the current machine's VM or private runtime state.

The best description today is **a guarded private-server research prototype with working real-client bots - not yet a polished, portable or unattended hosting product.**
